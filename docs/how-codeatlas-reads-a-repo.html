CodeAtlas internals

How CodeAtlas reads a repo

CodeAtlas never runs your program. After the clone it parses the source into syntax trees and writes down only what it can prove: a graph of nodes and edges, each edge carrying the file and line that justify it. Every "flow" you see in the UI is assembled later, in the browser, by walking that graph.

This page follows one analysis from the moment you press Analyze to the moment a tab can draw. Stages are numbered in the order the code runs them. The Java analyzer gets the most space because it does most of the extraction. A worked trace through demo/ledger shows the rules applied to real code.

Read from: core/internal/analysis · core/internal/scan · analyzers/java · analyzers/typescript · analyzers/infra · core/internal/store · core/internal/graph · web/src/graph. Current as of 21 October 2026.

Before the steps

What gets produced: the IR graph

Every analyzer writes the same format, the IR (intermediate representation, ir/schema/ir.v1.schema.json). Knowing its shape makes every later step easier to follow.

node
id, kind, name, parent (containment), location (file, start/end line), attrs (free-form facts), otel (the OpenTelemetry names runtime data will use for the same thing)
edge
source, target, kind, locations (every line where it happens, up to 20), attrs
Node kindsEdge kinds
service, module, package, file, class, interface, enum, function, method, field, endpoint, database, table, topic, queue, external, container, deployment contains, imports, depends_on, calls, extends, implements, references, handles, reads, writes, publishes, consumes, http_calls, deploys, connects_to, runs

IDs are computed, not counted

Every ID is built from what the thing is, so two runs, two commits or two analyzers that see the same thing produce the same ID. Merging and comparing depend on this.

Stage 1 Server · core/internal/analysis

Clone

Pressing Analyze sends POST /api/v1/repos/{repo}/analysis. The server's Runner takes it from there.

  1. Queue. The request is refused if the repo has no git URL or already has a queued or running job. Otherwise a job is created in state queued.
  2. Wait for the slot. The server runs one analysis at a time. The time limit (CODEATLAS_ANALYSIS_TIMEOUT) starts once the slot is taken, so waiting in the queue doesn't count. Cancel kills the context, which kills git or the analyzer process.
  3. Make a workspace. A temp dir codeatlas-analysis-* with src/ for the checkout and ir/ for analyzer output. It is deleted at the end whatever the outcome; nothing of your code stays on disk.
  4. Pick credentials. See the table below. In every case git runs with GIT_TERMINAL_PROMPT=0, an empty GIT_ASKPASS and GCM_INTERACTIVE=never, so it fails instead of waiting for a password nobody can type.
  5. Clone. git clone --depth=1 --quiet -- <url> src. Only the latest commit of the default branch is fetched, with no history. Credentials in the URL are removed before it's logged.
  6. Identify the commit. git rev-parse HEAD gives the commit SHA every snapshot is filed under; rev-parse --abbrev-ref HEAD gives the branch. State becomes analyzing.
  7. Hand over to the scanner (stage 2) with the checkout path, repo name, commit and branch.
Repo settingHow git authenticates
Git profile chosenGIT_SSH_COMMAND="ssh -i <profile key> -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=accept-new" plus -c url.git@github.com:.insteadOf=https://github.com/, so an https GitHub URL also goes over SSH with that key. Fails early if the profile or its key file is missing.
No profile, server token setYour own credential helpers are switched off (they can open a keychain dialog and hang). A single helper answers only for CODEATLAS_GIT_TOKEN_HOST with user x-access-token and the token. The token travels in the environment, never in the command line.
NeitherThe server user's own git and SSH setup, with SSH forced into batch mode.

Final states are succeeded, failed (with git's last stderr line, or "timed out after …") or canceled. The job log keeps the last 400 lines. Jobs live in memory only: a server restart forgets the run history but not the stored snapshots.

Stage 2 Server · core/internal/scan

Detect languages and launch analyzers

The same scanner runs on the server and in the codeatlas CLI, so a CI upload and a UI analysis produce identical output.

  1. Detect. Walk the checkout, skipping hidden directories and node_modules, target, build, dist, vendor. Any .java file turns on the Java analyzer. Any .ts .tsx .js .jsx .mjs file (not .d.ts) turns on the TypeScript analyzer. The infra analyzer always runs. The walk stops once both languages have been seen.
  2. Locate. Each analyzer is found from its env var (CODEATLAS_JAVA_ANALYZER, CODEATLAS_TS_ANALYZER, CODEATLAS_INFRA_ANALYZER), then next to the server binary, then in the source tree's build output. Java runs as java -jar codeatlas-java.jar, TypeScript as node dist/src/main.js.
  3. Run each as its own process: <analyzer> <checkout> --repo NAME --commit SHA [--branch B] --out ir/<lang>.ir.json. Its stdout and stderr go straight into the job log.
  4. Read and validate the output file (stage 6), then store it before moving to the next analyzer.
Why separate processes

A crash or a missing toolchain in one analyzer doesn't stop the others. The job ends failed and names the failures ("analyzers failed: typescript"), but snapshots from analyzers that succeeded are already saved and visible.

Stage 3 analyzers/java

Java analyzer

This is where most of the extraction happens. It is built on JavaParser (syntax trees) with its symbol solver (which works out what a name refers to). It makes fixed passes over every parsed file. The order matters: later passes look up tables that earlier passes filled. I/O detection, for example, can only trace a table name back through callers once the full call graph exists.

  1. Find build modules; read each module's config files
  2. Parse every source file
  3. Declare modules, packages, types, fields and methods
  4. Spring Data repositories and JPA entity tables
  5. Package imports, inheritance, field references, entity relations
  6. Spring endpoints, Feign clients, message listeners
  7. Give lambdas that run as their own task a node
  8. Call graph, with the conditions around each call
  9. I/O: framework calls, then plain-Java clients (uses value tracing and SQL reading)
  10. Link outgoing TCP connections to servers found in the repo
  11. Mark entry points: main, threads, scheduled jobs
  12. Async edges: where work is handed to another thread
  13. Config keys and environment variables read
  14. Control flow and variables for every method and task lambda
  15. Build the document, dropping dangling references

3.1Find modules and read config

ProjectLayout walks the repo (skipping .git target build out node_modules .idea .gradle bin).

  • A module is a directory with pom.xml, build.gradle or build.gradle.kts that has sources: src/main/java, or the <build><sourceDirectory> its own pom or a parent pom declares, resolved relative to the module the way Maven does. A repo with no build files at all is treated as one module.
  • Name: the pom's <artifactId>, else the directory name. App name: spring.application.name if set, else the name.
  • Config map (from src/main/resources only), in this order, first file to define a key wins:
    1. application.properties
    2. application.yml/.yaml, first YAML document only (later documents are usually profile overrides), flattened to dotted keys
    3. every other *.properties, *.config, *.cfg alphabetically, with .example/.sample/.template/.dist copies last (they only fill keys the real files lack)
  • Key → file index: for every key, which files mention it. Used later to say "read from processor.properties".
  • Database: spring.datasource.url, else the first value anywhere that starts with jdbc:. jdbc:<system>://<host>[:port]/<db> gives system, host and database name; jdbc:h2:mem:testdb gives system and name. postgres becomes postgresql, sqlserver becomes mssql.
  • Redis host: the first of spring.data.redis.host, spring.redis.host, redis.host, redis.hostname, cache.redis.host that isn't a ${…} placeholder.
# demo/ledger/src/main/resources/processor.properties
db.url=jdbc:postgresql://ledger-db:5432/ledger   → postgresql, host ledger-db, db ledger
db.trades.table=trade_book                        → used by value tracing (see the worked trace)
redis.host=ledger-cache                           → Redis node db:redis/ledger-cache

3.2Parse

One JavaParser instance at Java 21 language level. Its symbol solver combines JDK reflection (for java.* types) and every module's source roots (for your own types). Files that fail to parse are logged and counted; the rest continue.

Important

Your dependencies' jars are not given to the solver. Spring, Kafka, Netty and Jedis types are known only by the names written in your code. That is why detection keys on simple type names (KafkaTemplate, Jedis, ServerBootstrap), and why almost every resolution step has a fallback for when the solver gives up.

With no declaration, a @SpringBootApplication class, else every class with a main the launcher accepts. One program: the module is that service. Several: the module stays a module holding the code, and each program is its own service (attrs.mainClass, attrs.jar, attrs.module, a runs edge to its main). Two lookup rules are used by every later pass:

Resolving a type name

For a type written in code, try in order and stop at the first hit: the written name is already a known FQN → a single-type import with that simple name → same package → a nested type of an enclosing class → a wildcard import that contains it → the simple name is unique in the repo → the symbol solver. If none works and it isn't in the repo, the answer is "unknown".

Finding a call's receiver type

For orders.save(x): find where orders is declared, in this order: a parameter of the enclosing method, a local (unless declared with var), a field in scope. Resolve that declared type with the rule above. Only if there's no declaration does it ask the solver to type the expression. Reading declarations first is faster, and it works when the solver can't load a library type.

3.4Entities and repositories (Spring/JPA)

These run before any call analysis because later passes need two lookup tables: repository → entity and entity → table.

  • Repository: an interface extending one of Repository, CrudRepository, ListCrudRepository, PagingAndSortingRepository, ListPagingAndSortingRepository, JpaRepository, MongoRepository, ReactiveCrudRepository, R2dbcRepository, ElasticsearchRepository with type arguments. The first type argument is the entity.
  • Entity table: a class with @Entity. Table name from @Table(name=…), else snake_case(ClassName). It belongs to the module's database node (db:<host>/<db>; if the URL is unknown, db:<app>/<app>-db with system "unknown").
  • Columns from fields, including those inherited from @MappedSuperclass parents:
    • skipped: static, transient, @Transient, @OneToMany, @ManyToMany, @ElementCollection, @Embedded, and the mappedBy side of @OneToOne
    • @ManyToOne/@OneToOne → foreign-key column named by @JoinColumn(name) or <field>_id
    • other fields → @Column(name) or snake_case(field)
    • @Id/@EmbeddedId → primary key; nullable=false, unique=true, optional=false recorded
  • An edge entity class → table (references, via: jpa), so a class diagram and the data model connect.

3.5Structural relations

  • Package dependencies: each single-type import of an in-repo type from another package adds to a depends_on edge, with attrs.imports counting them.
  • Inheritance: extends/implements to in-repo types (an interface extending an interface is extends, as in UML). Library supertypes (Runnable, ChannelInboundHandlerAdapter) are kept as text on the class.
  • Field references: a field whose type mentions an in-repo type anywhere (including generic arguments and arrays) gives a references edge listing the field names, with many: true for arrays and List/Set/Collection/Iterable/Map/Optional.
  • Table relations: for entity fields with @ManyToOne, @OneToOne or @ManyToMany (not the mappedBy side) pointing to another entity, a table → table edge with cardinality and the join column or join table.

3.6Declared endpoints, clients and listeners

These are found from annotations alone, without looking inside method bodies.

Spring MVC endpoints

  1. Only classes with @RestController or @Controller.
  2. Class prefixes from @RequestMapping(value|path).
  3. Each method with @Get/Post/Put/Delete/PatchMapping, or @RequestMapping(method=…) (no method means ANY).
  4. Every prefix × path × verb becomes an endpoint. Routes are joined, slashes collapsed, regex constraints removed ({id:\d+} → {id}), trailing slash dropped.
  5. Edge endpoint handles → handler method.
  6. Data shapes: @RequestBody parameter → attrs.request; @PathVariable, @RequestParam, @RequestHeader, @CookieValue → attrs.inputs; the return type → attrs.response, unwrapping ResponseEntity, Optional, Mono, Flux, CompletableFuture, CompletionStage, HttpEntity, DeferredResult, Callable, ConsumerRecord, Message to their last type argument.

Feign clients

@FeignClient(url | name | value) → an external node for the host (a bare service name is accepted as a host). Each mapped method → http_calls with verb, path, client feign, payload (the @RequestBody type, else params(a, b)) and response type.

Message listeners

@KafkaListener(topics|value) → consumes a topic; @RabbitListener(queues) and @JmsListener(destination) → consumes a queue. The payload type is the @Payload parameter, else the first parameter that isn't a header or an Acknowledgment, Channel, MessageHeaders or Consumer.

3.7Lambdas that run as their own task

Code inside new Thread(() -> …) runs later, on another thread. If its calls were credited to the method that created the lambda, that method would look like it does the work. So these lambdas get their own method node first:

Lambda passed toNode name
server.createContext("/x", λ)λ handler /x (line N)
schedule, scheduleAtFixedRate, scheduleWithFixedDelayλ scheduleAtFixedRate (line N)
submit, execute, runAsync, supplyAsync, invokeAllλ submit (line N)
new Thread(λ)λ thread (line N)

ID method:<class>#lambda@<line>(), parent = the class, attrs.definedIn = the method that created it. From here on, every lookup of "which function does this code belong to" (callerOf) returns the innermost such lambda, else the enclosing named method or constructor.

3.8Call graph and the conditions around calls

For every method call expression in every file:

  1. Caller: callerOf(call), as above.
  2. Target, first try: the symbol solver resolves the call to a declaration. If it is in the repo, that's the target.
  3. Target, fallback: take the receiver's declared type (or the enclosing class when there's no receiver). Look for methods with the same name and the same number of arguments (or varargs). Exactly one → that's it. More than one → give up, since overloads can't be told apart without argument types. None → repeat in the in-repo superclass.
  4. Record: a calls edge with the line and guards (below), plus three tables for later passes: what this call resolved to (for control flow), the target (for value tracing), and the call site under the target (to find "who passes what to this parameter").

new X(…) is handled the same way: the resolved constructor, or the only constructor of X with that many parameters (anonymous classes excluded). The edge is named new X.

Calls into library code don't produce calls edges. They are what pass 9 inspects for I/O.

Guards: under what condition does a call run?

From the call, walk up the syntax tree to the function boundary. Each enclosing structure the call sits in adds one condition, outermost first:

Call sits inCondition text
if (c) then / elseif c / if not (c)
c ? a : bif c / if not (c)
case A, B / defaultif sel is A or B / default case of sel
for-each / for / while / dofor each x in xs / loop while c / while c / repeat while c
catch (E e)on E
right side of a && b / a || bif a / if not (a)
lambda passed to ifPresent, orElseGet, forEach, exceptionally, onErrorResume…if present, if empty, for each, on error

The chain is joined with › and stored on the edge in conditions (up to 10 distinct chains). If any occurrence has no guard, unconditional: true is set and diagrams draw a solid line; otherwise the line is dashed and labelled. Condition text is the source code itself, shortened to 90 characters.

Who gets credited with the I/O

Value tracing can return a value together with the call site where it was supplied. The rule:

  • If the value came through a parameter, the edge starts at the caller that supplied it, and attrs.via names the method that did the I/O. A generic KafkaWriter.send(topic, msg) called by OrderService with "orders" shows as OrderService publishes orders, via KafkaWriter.send. That's the useful reading.
  • If the value came through a field, the call site is dropped. A value stored in a field was configured earlier (typically at startup), so the startup code didn't do the I/O. The method doing the I/O keeps the edge.
  • Otherwise the method containing the I/O call gets the edge.

What a consumer decodes into

Inside the consuming method, or else the wrapper class around the consumer, look for a call that takes record.value() as an argument:

  • a Foo.class argument (mapper.readValue(record.value(), Trade.class)) → Trade
  • an in-repo method whose return type is an in-repo type (Trade.parse(record.value())) → that type
  • a library decoder parseFrom, parse, decode, fromBytes, deserialize, readFrom, parseDelimitedFrom on a capitalised type (protobuf) → that type name

Marking the call for control flow

Every expression that caused an effect is noted, so when the control flow is built (3.14) that line shows as "INSERT trade_book" or "send orders" instead of an anonymous library call.

3.10Value tracing: what string can this be?

Plain Java builds names at run time: "INSERT INTO " + tableName, props.getProperty("topic.trades"). Values works out every string an expression can take, without running anything. Each result is a value text plus, optionally, the call site that supplied it.

Bounds: at most 16 values per expression and 10 steps deep; an expression already being evaluated is skipped (no infinite loops on recursion). Results are de-duplicated by text and site.

Two views of the result: known() keeps only values with no * (used for topics, ports, paths). of() keeps partial ones like position:*:* (used for SQL and Redis keys, where a pattern is still informative).

Choosing the best pattern: for Redis keys, representative() drops a value when another one from the same site covers it and is at least as specific. position:: (a helper's empty default) gives way to position:*:*, and *:*:* gives way to it too.

Topic fallback: when no topic name can be traced (the code picks it from a map filled at run time, say), every config value under a key matching topic / topics / destination / channel is used instead. Those edges carry inferred: config and the configKeys they came from, so the UI can tell guesses from traced facts.

3.11Reading SQL text

Sql.read isn't a full SQL parser. It reads just enough to say which tables a statement reads and writes, and which columns it names. Rules, in order:

  1. The statement must start (after comments) with SELECT, WITH, INSERT, UPDATE, DELETE, MERGE, UPSERT, REPLACE, TRUNCATE, CALL, EXEC or COPY. Otherwise it's not SQL.
  2. Quoted string literals are blanked, so 'FROM x' inside a value is ignored.
  3. Writes: INSERT/UPSERT/REPLACE [IGNORE] INTO t (cols), UPDATE [ONLY] t, DELETE FROM t, MERGE INTO t, TRUNCATE [TABLE] t, COPY t (cols) FROM.
  4. Reads: every table after FROM, JOIN or USING, except pseudo-tables (select, lateral, unnest, values, dual, generate_series).
  5. For UPDATE and DELETE, the target is removed from reads (UPDATE t … FROM other writes t and reads other).
  6. Columns: the INSERT/COPY column list, or a SELECT list (aliases win; * and bare expressions are ignored).
  7. Identifiers may be quoted or schema-qualified; a schema that is * (unresolved) is dropped. A table that is * stays "unknown", and the caller attaches the edge to the database instead.

3.12Entry points and work started on other threads

Entry points (attrs.entryPoint)

  • main: a main the java launcher would run (JLS 12.1.4): void, not private, String[] / String... or no arguments (the array form wins), static or an instance method on a class the launcher can construct. A main inherited from a superclass counts when the build names the subclass. A main no jar starts still has the mark, with packaged: false.
  • scheduled: @Scheduled (its annotation text kept as schedule), or the task handed to schedule* (method reference, task lambda, or new X() with run/call). The schedule text records the call's other arguments, e.g. scheduleAtFixedRate(0, interval, MILLISECONDS).
  • thread: run() or call() with no parameters in a class that is a Thread, Runnable, Callable or TimerTask, directly or through in-repo supertypes (up to 4 levels).

HTTP and socket handlers and message consumers are not marked here. They are recognised from their handles and consumes edges.

A task expression resolves to: a method reference's method; a task lambda's node; or, for new X() or a variable/field of type X, X's run()/call() with a body, searching in-repo superclasses up to 5 levels (only if X is a Thread/Runnable/Callable/TimerTask). The edge keeps the guards, so "starts TradeConsumer only if batching is off" is preserved.

Why mark them

Views that follow a request (Flow, Sequence, Data flow per endpoint) must not follow these edges. The request doesn't wait for a background thread. The Program view does follow them, because it shows everything a program starts.

Servers opened (attrs.openedBy)

For each Netty or JDK HTTP server endpoint: the method that calls bind/createContext, plus the method where the port or path value came from. That's how the program view knows main opens "TCP :9000" even when the bind happens two calls down.

3.13Config and environment reads

  • System.getenv("NAME") → NAME added to the method's envReads.
  • getProperty / getString / getOrDefault / getInt / getLong / getBoolean / getValue / getRequiredProperty / get with a constant key that exists in the module's config → configReads {key, file}. When several files define the key, the file the class mentions by name ("processor.properties") is chosen.

3.14Control flow and variables

Last, every method, constructor and task lambda body is turned into a list of steps. This is the "inside" of a function; the Activity, Sequence and Program views draw it.

Calls inside each step come from the resolution tables of passes 8–12, so a call already knows whether it is calls (in-repo method), reads/writes/publishes/consumes/http_calls/connects_to (with its target node), or an async start. They are listed in evaluation order (arguments before the call that uses them). A call guarded within the statement (by a ternary, &&, or a lambda) gets a when. Calls inside a task lambda are left out of the enclosing method; they belong to the lambda's own control flow.

Size cap: past 400 statements a method is cut to its first 20 steps plus "… (method too large to chart)", so generated code can't bloat the graph.

Variables: each parameter, local, captured variable (from an enclosing function), field and static is listed with its scope, type, declaring class, first line, read and write counts, and final. Writes count assignments, ++/-- and calls of mutating methods on it (add, put, remove, clear, compute, incrementAndGet, append, sort…). Up to 60 variables per method.

3.15Building the document

Throughout all passes the builder keeps one node per ID (re-declaring returns the existing node) and one edge per (source, target, kind). A second occurrence adds its line to locations (up to 20) and its guard chain to conditions. At the end, edges to unknown nodes and self-edges are dropped, and parents pointing at unknown nodes are cleared. The document is written as JSON with the source block: repo, commit, branch, analyzer name and version, generation time.

Worked trace · demo/ledger

Two facts, followed from code to graph

The Java rules above, applied to two questions about the demo ledger processor.

"Which table does TradeWriter write to?"

// ProcessorMain.main
TradeWriter writer = new TradeWriter(dataSource, config.getProperty("db.trades.table"));

// TradeWriter
public TradeWriter(DataSource dataSource, String tableName) {
    this.tableName = tableName == null || tableName.isBlank() ? "trade_book" : tableName;
}
public void insert(List<Trade> trades) {
    String sql = "INSERT INTO " + tableName
        + " (trade_id, account_id, account_email, symbol, quantity, price) VALUES (?, ?, ?, ?, ?, ?)"
        + " ON CONFLICT (trade_id) DO NOTHING";
    try (Connection conn = dataSource.getConnection(); PreparedStatement ps = conn.prepareStatement(sql)) { … }
}
  1. Spot it (3.9 B). conn.prepareStatement(sql): the name is on the JDBC list, the receiver type Connection isn't in the repo, there's an argument. Run jdbc().
  2. Trace sql (3.10). A local → its initializer → a + chain: combine the parts.
  3. Trace tableName. Not a local or parameter of insert, so a field. No initializer. One assignment in the class, a ternary: the then branch gives "trade_book"; the else branch is tableName, which inside the constructor is a parameter.
  4. Walk call sites. Call sites of the constructor (from 3.8): new TradeWriter(dataSource, config.getProperty("db.trades.table")). Argument 2 is a config lookup with a constant key. The module config (3.1) has db.trades.table=trade_book.
  5. Credit. The value reached insert through a field, so the call site in main is dropped. The edge belongs to TradeWriter.insert; main only configured the writer.
  6. Read the SQL (3.11). Both variants are the same text: INSERT INTO trade_book (trade_id, …) …. Verb INSERT; writes trade_book; columns trade_id, account_id, account_email, symbol, quantity, price. No FROM, so no reads.
  7. Name the nodes. Database from db.url: db:ledger-db/ledger (postgresql). Table table:ledger-db/ledger.trade_book. No entity declares it, so the SQL columns are merged into its columns.
  8. Emit. TradeWriter.insert —writes→ trade_book, operations [INSERT], payload {type: "trade_book row", fields: […]}, location = the prepareStatement line, unconditional (a try resource isn't a guard). truncate() separately yields a TRUNCATE write.
  9. Mark the line (3.9). In insert's control flow, the try step's resource call reads "INSERT trade_book".
  10. In the browser (8). The column name account_email matches the email rule, so every flow into this table is flagged as carrying personal data.

"Which topic does TradeConsumer read, and who starts it?"

// TradeConsumer implements Runnable
private static final String TOPIC = "trades";
public void run() {
    try (TopicReader reader = new TopicReader(kafka, TOPIC)) {
        while (!Thread.currentThread().isInterrupted()) {
            for (ConsumerRecord<String, byte[]> record : reader.poll()) {
                Trade trade = Trade.parse(record.value());
                book.apply(trade);
                writer.insert(List.of(trade));
            } … } } }

// TopicReader(Properties props, String topic)
this.consumer.subscribe(Collections.singletonList(topic));

// ProcessorMain.main
if (Boolean.parseBoolean(config.getProperty("batching", "true"))) { new TradeConsumerThread(kafka, book, writer).start(); }
else { new Thread(new TradeConsumer(kafka, book, writer), "trade-consumer").start(); }
  1. Spot it (3.9 B). consumer.subscribe(…): the receiver is the field consumer, declared KafkaConsumer, whose name ends in "Consumer" and isn't in the repo. Run kafkaSubscribe().
  2. Trace the topic. singletonList passes its argument through → topic, a parameter of the TopicReader constructor → its call sites → new TopicReader(kafka, TOPIC) in TradeConsumer.run → TOPIC is a constant "trades". The value remembers that call site.
  3. Credit. It came through a parameter, so the edge starts at the supplier: TradeConsumer.run —consumes→ topic:trades, via: TopicReader constructor. TradeConsumerThread's own new TopicReader gets its own edge the same way.
  4. Payload. Inside run, Trade.parse(record.value()) takes the record value and resolves to an in-repo method returning Trade, so the payload is Trade, linked to its class.
  5. Entry point (3.12). TradeConsumer implements Runnable and run() has no parameters, so it's entryPoint: thread.
  6. Who starts it. new Thread(new TradeConsumer(…)) in main → the task is an in-repo Runnable → main —calls(async: thread)→ TradeConsumer.run, with condition if not (Boolean.parseBoolean(config.getProperty("batching", "true"))). (The trailing .start() is on a JDK Thread, so it adds nothing.)
  7. In the browser (8). The Program view starts at main, follows that async edge, and draws a part "Consume trades · …" (a thread, TradeConsumer.run) started by start-up "when not batching". Topic trades appears in the Data in lane. The digest of run reads: loop while not interrupted → loop for each record → Trade.parse → PositionBook.apply → TradeWriter.insert → INSERT trade_book.
Stage 4 analyzers/typescript

TypeScript / JavaScript analyzer

Same output shape, built on ts-morph (the TypeScript compiler API). The control-flow steps and SQL reader are ports of the Java ones, so both languages render identically. Differences worth knowing:

Packages, not build modules

Each directory with a package.json and sources is a package. It is a service if it depends on a server or worker library: express, @nestjs/core, fastify, koa, @hapi/hapi, next, hono, kafkajs, amqplib, ws, socket.io, node-cron, cron, bullmq, bull. Each package gets its own compiler project (its tsconfig if present, JS allowed, decorators on), excluding nested packages.

Order of passes per package

  1. Prisma schema → tables (models, fields, relations, datasource provider)
  2. Declare files, directories, functions, classes, methods
  3. TypeORM @Entity classes → tables and columns
  4. Express router mounts (app.use("/api", router)) → route prefixes
  5. Entry modules: files that run code at top level and are not imported by another file, or are named by package.json main/bin → a "(module)" function with entryPoint: main
  6. Scheduled and threads: setInterval (every N ms), cron.schedule/scheduleJob, new CronJob, Nest @Cron/@Interval/@Timeout; new Worker("./w.js") marks that file as a worker-thread entry
  7. Per file: imports/inheritance, routes (Express verbs on routers and apps, NestJS @Controller + @Get/@Post…), calls and I/O
  8. Control flow, variables and doc comments for every declared function

Calls and I/O

  • Call targets come from the compiler's declaration lookup. new X() links to X's constructor.
  • HTTP: fetch(url, {method, body}), axios.get/post…, axios({url, method, data}), got.
  • Kafka (kafkajs): producer.send({topic}), consumer.subscribe({topic | topics}).
  • SQL: query, execute, exec, run, all, get, prepare, many, one, none, any… with SQL text, plus tagged templates sql`SELECT …` (postgres.js, slonik).
  • Redis (ioredis, node-redis), RabbitMQ (amqplib sendToQueue/publish/consume on a channel), Prisma (prisma.model.op()), TypeORM repositories (Repository<Entity> receivers).
  • Inbound sockets: net/tls/http.createServer(handler).listen(port), ws WebSocketServer({port}) with on("connection").
Limit

Value resolution is simpler than Java's: constants, template literals (substitutions become *), a ?? "default", + chains, and variable or enum initializers. It does not walk back through callers' arguments or return values, so names passed in as parameters stay unresolved.

Stage 5 analyzers/infra

Infra analyzer

Reads YAML and JSON files under 5 MB (skipping the usual build directories) and recognises three kinds of document.

docker-compose files

  • Each service → container node ctr:<name> with image, a role matched from the image name (database, cache, broker, proxy, search, observability), buildContext (resolved relative to the compose file), ports.
  • What it starts: the service's command / entrypoint, else the ENTRYPOINT / CMD of the last stage of the Dockerfile it is built from (build.dockerfile, default Dockerfile; recorded as dockerfile), plus the jar files that stage COPYs in. From these: jars (file names, possibly a glob such as producer-*.jar) and mainClasses (plain dotted arguments; option values like -Dkey=a.b are skipped). Nothing else from the Dockerfile is kept, since ENV and ARG values can hold credentials.
  • Environment: a telemetry service-name variable becomes serviceName. Only the keys of other variables are kept; values often hold credentials.
  • connects_to edges from depends_on, links, and any environment value that mentions another service's hostname (a URL or a broker list), recording which variable.

Kubernetes manifests

  • Workloads (Deployment, StatefulSet, DaemonSet, ReplicaSet, Job, CronJob) → deployment nodes k8s:<namespace>/<name> with their pod labels, and jars / mainClasses from each container's command and args.
  • After all files: each Service whose selector matches a workload's labels (same namespace) gives that workload hostnames: svc, svc.ns, svc.ns.svc.cluster.local. Those are the names other code uses to call it.
  • Each Ingress → an external node for its host, connects_to the workloads behind its backend service, with paths.

OpenAPI / Swagger specs

Each operation → an endpoint with the same ID scheme as the code analyzers. The service is chosen from x-service-name, else a server host that looks like a service name, else the title. A spec and the controller implementing it merge into one node.

.codeatlas.yml

Diagram groups and renames from the repo root are attached to the infra document as config and passed through to the UI unchanged.

Stage 6 core/ir · core/internal/store

Validate and store

  1. Strict decode. Unknown JSON fields or trailing data are errors, so a wrong analyzer version can't slip half-understood data in.
  2. Validate. IR version; repo, commit and analyzer present; every node has an ID (unique), a known kind and a name; parents and edge ends exist; no node contains itself; edge kinds known; locations have a file and line numbers ≥ 1 in order. Up to 100 problems are listed in the job log. Any problem rejects the whole document.
  3. Save in one transaction. Delete any earlier snapshot for the same repo, commit and analyzer (re-analyzing the same commit replaces it). Insert the snapshot row (analyzer, versions, counts, config). Bulk-copy nodes and edges into their tables, with attrs, otel and locations as JSON.

A commit therefore has up to three snapshots: java, typescript and infra. Nothing is merged at write time.

Stage 7 core/internal/graph

Merge on read

When a tab asks for a repo's graph, the server loads every snapshot of the requested commit (the latest commit if none), ordered so the infra snapshot comes last, and merges them:

  1. Union nodes by ID. For the same ID, the first non-empty value wins for qualified name, parent, language and location; attrs and otel maps are combined, earlier values winning on clashes.
  2. Union edges by (source, target, kind), concatenating their locations.
  3. Link containers to code. A container or deployment deploys a service when its build context equals the service's module path. When that directory builds several programs, it deploys the one whose jar (glob patterns match) or main class its command names, and nothing if none or more than one matches. Otherwise it links when its name, telemetry service name or any of its cluster hostnames equals the service's name. It also deploys a database whose connection host is one of those names.
  4. Link databases with no known host. When the URL comes from the environment (Prisma's DATABASE_URL, say): if a service's container connects to exactly one database container, and the service uses exactly one still-unlinked database node, they're linked.
  5. Turn "external" hosts into services. An external node whose host equals a service name, a telemetry service name, or a container's name or hostname is really another service in the repo. Its edges are retargeted (through the container to the service it deploys), and the external node is removed. http://inventory-service/items becomes orders → inventory instead of orders → external.
  6. Filter by the requested node kinds, if any, keeping only edges between kept nodes.
Stage 8 web/src/graph

How flows are built in the browser

The analyzers record local facts: "this method calls that one", "this method writes that table". Flows across many methods are built in the browser from those facts. These are the core rules, leaving out drawing and layout.

Lifting to an owner

For each edge, both ends walk up their parent chain to the nearest node of the level being drawn: service, module, database, topic, queue or external for Architecture; package for Components. Edges whose two ends land on the same owner disappear; the rest are merged per pair, keeping the set of underlying kinds. TradeWriter.insert writes trade_book becomes ledger-processor → ledger-db.

Programs that share a module

When a module builds several programs, each program is a service with a runs edge to its main and attrs.module pointing at the module that holds the code. Its code is found by walking from that main:

  • calls (async ones included: work it starts on other threads runs in the same process) and handles;
  • every endpoint whose openedBy is reached, and that endpoint's handler;
  • a call to an abstract method reaches the in-repo methods with the same name and parameters in its subtypes;
  • reaching a constructor reaches the class's thread body (run / call), however the object is later started (consumers.forEach(pool::submit));
  • a Spring Boot main also reaches every endpoint, consumer and scheduled job of its module.

For lifting, a node in such a module belongs to every program that reaches it, so shared code is credited to each of them. A method no program reaches (a framework callback like Netty's channelActive, an overload, a stop hook) belongs to the programs that reach something in its class. Only code in classes no program touches stays with the module, which is drawn only if such code does I/O. Calls between two pieces of the same module are never a link between programs. A program's box says which module it comes from (java · from livepnl).

Reachability

Breadth-first search from a start method along calls and handles edges to methods and functions. Async edges are skipped unless the view asks for them. The default cap is 80 methods and depth 10; the Program view uses 150 and 12. Flow drops leaf getters and setters (named get/set/is/has, with no calls or I/O).

Entry points of a service

Endpoints inside the service (their start is the handles target; TCP endpoints count as socket), methods with consumes edges (consumers), and methods with attrs.entryPoint (scheduled, thread, main). Sorted in that order.

Data flow (DFD)

  • Level 2 (one service): each entry point is a process. Inputs: a client (or calling services, if the service isn't public; "socket client" for TCP) sends the request type and receives the response type; a consumed topic sends its payload type. Then every side-effect edge on methods reachable from the entry: reads (store → process, response types), writes and publishes (process → target, payload types), HTTP and TCP calls (both directions).
  • Folding: entry points of the same kind whose flows have the identical signature are drawn once as "×N", provided they touch data beyond answering the caller.
  • Level 1 and 0: processes are services; at level 0 the whole repo is one process and only the outside world remains.

Reading rules (every tab)

Every diagram goes through one pass (web/src/graph/reading.ts) so all tabs read like the Program tab:

  • Direction. Each line points from where data comes from to where it goes. A read is drawn from the store to the reader, a write from the writer to the store; a store both read and written by one box is a single line from the writer with arrowheads at both ends (two opposite lines would be a cycle the layout breaks at random). Consumed topics point at the consumer, requests at the callee. ELK is told how much each line's direction matters (elk.layered.priority.direction): data lines most, calls next, structure (uses, inheritance, deployment, loop-backs) least, so when the layout must break a cycle it turns a structural line, never a data line.
  • Lanes (Architecture, Data flow, Components, Explore package level, Flow). A data box only read by the parts goes in Data in; only written, or read and written by the same parts, in Data out; written by one part and read by another, between the parts. Data systems (Kafka, PostgreSQL) are copied per lane so each side keeps its own group.
  • Names. Services get rows for the requests they take (TCP / HTTP endpoints) and what their code does with data; packages and classes a row from their code's effects (and a class its doc comment); functions are named by their doc comment's first sentence, else their own I/O, with Class.method underneath; level-2 data-flow processes by what their work does; tables say which programs write and read them; containers which program they run.
  • Typed lines. Every line carries the types moving along it: payloads of writes, publishes and HTTP calls, what a read returns, a consumed topic's payload, the argument types of a call, an endpoint's request. The verb (reads, publishes, POST /x, a call's condition) is the second label line.
  • Order. Parts are numbered by their longest path from where data starts (ignoring lines that close a cycle); a part nothing feeds ranks with those its sources feed.
  • Folding. A data group with more than four members starts folded into one box (VGroup.fold).
  • Outline. The parts in order, each with what comes in and goes out (three or more same-typed links into one system read as one line: "byte[] → Kafka (8): live-prices, prices, fills +5"), and its rows. The Sequence tab lists participants with the messages they receive and send.

Program (one program read as one file)

  1. Pick a program: each service with a runs edge, then mains no build packages. Its root is the main it runs.
  2. Parts. Start-up (the main). Each async edge leaving a part's reach starts a part (thread, scheduled job, executor task, shutdown hook). Creating an object whose class has a thread body (run/call) starts that body as a part too (consumers.forEach(pool::submit) has no call edge). Each endpoint whose openedBy is reached is a server part; several ports served by one handler are one part. A Spring Boot main adds every entry point of its service.
  3. Whose code. A part owns its reach plus every method of its own thread class (a consumer that subscribes in its constructor), and never the methods of another part's thread class. Its data in and data out come from the code it owns.
  4. Names. A part is named by what it does. Start-up adds its main effects. A server part is "Receive <request type>" (or "Serve <route>"). A thread class leads with its own name unless the name is generic (Worker, Task, Main…), then its effects ("Price engine · read price-derivation:matrix"). Effects read "consume …", "publish to Kafka (8 topics)", "write …", "call …", "read …" (a store it also writes is not repeated). Underneath: the kind of work and Class.method. The doc comment's first sentence, or the starting method's for a lambda, is the first line in the box.
  5. Between parts. A started lambda carries what it captures (attrs.variables, scope captured): "transcode: int, sid: int, payload: byte[] · starts · via KafkaManager.submit". A queue links the part that puts into it (put, offer, add…) to the part that takes from it (take, poll, drainTo…), matched by element type because the two ends usually keep the queue in fields of different classes. Shared state (a map, list or atomic field) set by one part and read by another is a dashed line. A start that hands nothing on is a thin "starts" / "opens :5001" line.
  6. Order. Parts are numbered in the order data moves: start-up first, then each part after every part that feeds it; shutdown hooks last.
  7. Data in / out. The Data in lane collects the reads, consumes, inbound requests, config files and environment variables of each part's code; Data out collects writes, publishes, responses and outgoing calls. A data system with more than four members (eight Kafka topics) starts folded into one box.
  8. Outline. The same parts as text beside the diagram: how the program is started (java -jar producer-1.0.jar (maven-shade, pom.xml)), its entry point, then each part with started by / in / out / starts and its steps.

The digest inside each box walks the method's control flow: ? for if/switch/case, ↻ loops, ! catch, ✕ throw, ⇉ starting other work, → calls, and an I/O mark for reads and writes. A called method is opened inline (up to 2 levels) only if it decides something (has if/switch/loop/try) or reaches I/O within 4 calls; otherwise it's shown muted. Plain lines are kept only if they are calculations: an assignment with a compound operator (total += x), or one whose right side has arithmetic (pnl = (mid - avg) * qty), excluding strings and new.

Flow, Activity, Sequence

Flow is reachability from an endpoint's handler, drawn with conditional (dashed) edges. Activity draws one method's controlFlow steps directly. Sequence walks controlFlow in order, 3 calls deep: a lifeline per class, store, topic or remote service; if/loop/try become alt/opt/loop fragments. An HTTP call to another service of the repo continues into the handler whose route matches the path.

Sensitive data

Field and column names are lower-cased, stripped of punctuation, and tested against ordered rules; the first match wins (so cardToken is payment, not credential): payment, credential, government-id, email, phone, person-name (a bare name counts only on person-like owners such as Customer or User), address, birth-date, location, ip-address, financial. Nested in-repo types are followed 2 levels, so Order.customer.email is found.

Roles (for grouping)

A class's role comes from its stereotype, then its name suffix, then its edges: controllers and handled methods are Ingress; listeners and consumers, Messaging; entities, records and enums, Model; *Config/*Application, Config; repositories and DAOs, Persistence; Feign and *Client with HTTP calls, Integration; classes with only accessors, Model; anything else, Domain. A package takes its members' most common role.

Read before trusting a diagram

What it cannot see

Each limit below follows directly from the rules above. Knowing them explains most "why is this arrow missing" questions.

Interfaces stop the call tree

A call through an interface or abstract type resolves to the interface method, which has no body. No implementation is chosen, so reachability stops there. Injected service interfaces are the common case. Spring Data repositories are the exception, because their I/O is recognised at the call site.

Library types are known by name only

Dependency jars aren't loaded. A client wrapped in your own class is detected only because the wrapper's body uses a known client. A client type with an unfamiliar name isn't detected at all.

Ambiguous overloads

When the solver fails and a class has two methods with the same name and argument count, no edge is drawn rather than a guessed one.

Values have bounds

16 variants, 10 steps deep. Unknown parts become *. ${…} placeholders aren't expanded. Environment variables have no values at analysis time (only defaults). Topics from the config fallback are marked inferred and may over-attach.

SQL and ORMs

SQL is read with patterns, not parsed. Stored procedures (CALL/EXEC) name no tables. jOOQ, MyBatis XML, Hibernate HQL and Criteria queries aren't read.

Config scope

Only src/main/resources, and only the first document of application.yml, so profile-specific values are ignored.

Invisible by nature

Reflection, dynamic proxies, XML-wired beans, generated sources that aren't committed, and anything decided by data at run time.

Caps

400 statements per method chart; 20 locations and 10 condition chains per edge; 60 variables per method. Only the default branch head is analyzed (shallow clone, no history).
